# Schematics

## There is no schematic file, and that is deliberate

The vehicle is a **point-to-point perfboard build**. Drawing it in an EDA package would
produce a schematic symbol set, a footprint library and a netlist — of which only the
netlist describes anything real about a board with no copper traces on it. So the netlist is
what this directory holds, in the form that is actually useful: a table you can work through
with a multimeter, one row at a time.

| File | Contents |
|---|---|
| [`vehicle-netlist.tsv`](vehicle-netlist.tsv) | 25 nets, 87 connections, 23 reference designators |

---

## It cannot drift from the firmware

`vehicle-netlist.tsv` is generated by
[`tools/gen_netlist.py`](../../tools/gen_netlist.py), and every GPIO row carries the name
of the `flight::BoardPins` constant it comes from. **The generator refuses to write a
netlist whose pin numbers disagree with the header**, and it also fails if the firmware
assigns a GPIO that no net mentions.

```bash
python tools/gen_netlist.py
```

That check is what makes this file worth trusting. A hand-drawn schematic of a
point-to-point build is correct on the day it is drawn and wrong the first time a pin
moves; this one is wrong only if the generator is not run, and the build runs it.

**Do not hand-edit the TSV.** Edit `tools/gen_netlist.py` and regenerate.

---

## How to read it

Rows sharing a `net` value are one electrical node. So `+3V3` appearing on fourteen rows
means fourteen pins are on that node — the Pico's `3V3(OUT)`, four module supply pins, six
capacitors, the two radio and card star points, and the test link.

| Column | Means |
|---|---|
| `net` | The node name. Every row with the same name is the same piece of copper or wire |
| `class` | `power`, `i2c`, `spi`, `uart`, `radio`, `analogue`, `digital` — what kind of signal it is |
| `ref` | Reference designator. The full part list is in the file's own header comments |
| `pin` | Pin on that part. **Pico pins are physical numbers**, USB to the left, component side up — not GPIO numbers |
| `signal` | What the part's own silkscreen or datasheet calls that pin |
| `pin_constant` | The `flight::BoardPins` member the assignment comes from, where there is one |
| `note` | Anything that would cost an afternoon to rediscover |

**The `pin` column trips people up.** Pico physical pin 6 is `GP4`. The netlist gives the
physical number because that is what you count along the header with, and the `signal`
column gives the GPIO name because that is what the firmware calls it. The generator checks
that those two agree.

## Using it for continuity checks

This is the file's real job. After soldering, with the board unpowered:

1. Filter to one net.
2. Probe between the first row's pin and each of the others. All should read a short.
3. Probe between that net and every adjacent net. All should read open.

Step 3 is the one that catches the failure that matters — a bridged pin reads as a perfectly
good connection on step 2. Two nets worth doing first, every time: **`+3V3` against `GND`**,
and **`VBUS` against everything**, because pin 40 is live 5 V and nothing on this board
tolerates 5 V.

Record what you find in
[bring-up-record.md](../../documentation/testing/bring-up-record.md), not here.

## What is not in it

- **Wire gauge, colour and routing.** Those are in
  [assembly-procedure.md](../../documentation/hardware/assembly-procedure.md), which is
  where the floorplan and the coupling analysis live.
- **The ground-station bridge.** It is a Pico and an RA-02 with the same six SPI and control
  nets and nothing else — see [wiring.md](../../documentation/design/wiring.md).
- **Anything not yet fitted, marked as fitted.** The switch, Schottky, LEDs, resistors and
  test link are all in the parts list with `not yet fitted` against them. They are in the
  netlist because that is where the design says they go, and the mounting column is how you
  tell design from reality.
